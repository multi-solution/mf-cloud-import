# 初期設定ウィザード

このプラグインを使い始めるための設定を、対話で作ります。
**会計の専門用語は使わず、業務の実態を尋ねてください。** 科目や税区分はこちらで決めます。

## 進め方の原則

- **一度に1〜2問だけ聞く。** まとめて10問投げない
- **選択肢を出す。** 自由記述を求めない
- **推測できることは聞かない。** APIから取れる情報は先に取る
- 途中で失敗したら、**何が原因でどう直すか**を具体的に示す

---

## Step 1: つながっているか診断する

まず利用者に何も聞かず、以下を順に確認して**結果だけ**を表に出す。

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/preflight.py
```

（`${CLAUDE_PLUGIN_ROOT}` が未定義の環境では、このコマンドファイルが置かれた
プラグインのディレクトリを特定し、その `scripts/` を**絶対パスで**実行する）

- `mfc_ca` コネクタが使えるか（`mfc_ca_currentOffice` が返るか）
- 証憑の自動添付が使えるか（preflight の `status`）

**★`mfc_ca` のツールが見つからない場合**：プラグインはコネクタを同梱していない。
READMEの「2. MFクラウドのコネクタに接続する」の手順（claude.aiのコネクタ設定で
「マネーフォワード クラウド会計」を追加）を案内し、**接続が確認できるまで先へ進まない**。

```
✅ MFクラウド接続      OK（事業者：◯◯／個人・2026年度）
❌ 証憑の自動添付      認証が切れています
   → 直し方：ターミナルで次を実行してください
      python3 ${CLAUDE_PLUGIN_ROOT}/scripts/oauth_init.py
```

**証憑添付が使えない場合**、「記帳はできますが領収書の自動添付はできません。
先に認証を直しますか、それとも記帳だけ先に進めますか」と選ばせる。

`preflight` が `expired` のときは**ここで止まる**。認証を直さずに進むと、
証憑の付いていない仕訳ができてしまう。

## Step 2: 事業者の確認（最重要）

`mfc_ca_currentOffice` の結果をそのまま見せて確認を取る。

```
この事業者に記帳します。合っていますか？
  事業者名：◯◯
  種別：個人事業 / 法人
  会計期間：2026-01-01 〜 2026-12-31
```

**違うと言われたら、そこで停止する。** MFクラウド側で事業者を切り替えてもらう。
**事業者の取り違えが、この作業で最も重大な事故です。**

法人と個人事業を両方持っている利用者がいる。**どちらの帳簿かを必ず確定させる。**

**★証憑添付（REST認証）が有効な場合は、三点突合まで行う：**
preflight が返す `office_name` と `mfc_ca_currentOffice` の name が一致するか確認する。
不一致なら「記帳先と証憑の添付先が別の事業者になっています」と伝えて停止する
（REST認証を正しい事業者で `oauth_init.py` からやり直してもらう）。

**複数の事業者を扱う予定か**も、ここで確認しておく：

```
複数の会社・事業者の帳簿を扱う予定はありますか？

  1. この事業者だけ
  2. 複数を扱う予定
```

2 の場合：認証ファイルと台帳を事業者ごとに分ける必要があることを伝え、
`creds_path` を事業者ごとの別ファイル（例: `~/.mfc/credentials_◯◯.json`）に設定する。
`oauth_init.py --creds <パス>` で事業者ごとに認可してもらう。

## Step 2-b: 表示の好みを決める（★以降の質問の仕方が変わるので、先に聞く）

```
記帳のご経験について教えてください。表示のしかたを合わせます。

  1. あまり慣れていない
     → 専門用語を避け、理由も添えて説明します
  2. 経理の実務経験がある
     → 専門用語のまま、簡潔に表示します
  3. 税理士・会計事務所です
     → 事実と選択肢だけ提示します（確認を促す文言は出しません）
```

| 回答 | `user_profile` | `tax_review` |
|---|---|---|
| 1 | `beginner` | `on` |
| 2 | `expert` | `on` |
| 3 | `expert` | **`off`** |

**★3を選ばれた場合、以降「顧問税理士にご確認ください」という文言を出さない。**
相手が税理士本人なので、無意味なうえ実務の妨げになる。事実と選択肢だけを示す。

**★ただし、どの回答でも安全装置は一切緩めない**（証憑なしは仕訳しない／二重計上の防止／
売掛金はAPIで触らない／承認なしに登録しない）。これらは会計知識ではなく
システムの制約による事故防止のため、専門家にも同じく適用する。

この設定は後からいつでも変更できる旨を伝える（「専門用語で表示して」の一言でも切り替わる）。

## Step 3: 立替経費の貸方を決める

**聞き方（会計用語を使わない）：**

```
事業のお金と、プライベートのお金は分けていますか？

  1. 分けていない（自分の財布やカードで払うことが多い）
  2. 事業用の口座・カードから払っている
  3. 法人なので完全に分かれている
```

- 1 → `receipt_credit_account: "事業主借"`
- 2 → 使っている口座・カードを `getConnectedAccounts` から選ばせる
- 3 → `"未払金"` を基本にし、補助科目を選ばせる

## Step 4: 金額の基準を決める

```
食事代について。取引先との打ち合わせを兼ねた食事は、
いくらまでを「会議費」として扱いますか？（超えた分は接待交際費になります）

  1. 10,000円以下（よく使われる基準）
  2. 5,000円以下
  3. 金額で分けない
```

```
パソコンや備品を買ったとき、いくら以上なら「資産」として
分けて管理しますか？

  1. 100,000円以上（一般的な基準）
  2. 300,000円以上
  3. 決めていない（都度相談する）
```

**★これらは税務上の取り扱いに関わります。** 迷う場合は
「顧問税理士に確認してから設定することもできます」と伝え、**保留を選べるようにする。**

## Step 5: 過去の仕訳から勘定科目ルールを作る（★このプラグインの肝）

**必ず許可を取ってから実行する。**

```
過去1年分の仕訳を読んで、「この店ならこの科目」というルールを
自動で作れます。読み取ってよろしいですか？
（読むだけで、帳簿は一切変更しません）
```

承認されたら：

1. `mfc_ca_getJournals` で過去1年分を取得する。**`metadata.total_pages` を必ず確認し、全ページ取る**
   （結果は取引日順ではなく登録順に並ぶため、1ページ目だけでは網羅できない）
2. 摘要（`remark`）と勘定科目・補助科目・税区分の組み合わせを集計する
3. **同じ相手で科目が割れているものは候補にしない**（要確認リストに回す）
4. **件数が2件以下のものは候補にしない**（たまたまの1件をルール化しない）
5. **直近6か月を重く見る**（古い運用が今も正しいとは限らない）

提示のしかた：

```
過去1年の仕訳から、次のルールを作れます。
採用するものを選んでください。

  ✅ 「◯◯」→ 通信費        （12件中12件がこの科目）
  ✅ 「△△」→ 消耗品費      （8件中8件）
  ⚠️ 「□□」→ 会議費 or 接待交際費（5件中3件が会議費）… 割れているので都度確認にします
```

**★重要な注意を必ず添える：**

```
※ 過去の仕訳が誤っていた場合、その誤りをそのまま引き継ぎます。
   採用する前に、内容に心当たりがあるかご確認ください。
```

## Step 6: 二重計上になる組み合わせを確認する（★事故防止）

`mfc_ca_getConnectedAccounts` で連携の一覧を取り、**同じ買い物が2回入ってくる構成**が
ないかを確認する。

典型は、EC事業者を「EC連携」と「その支払いに使うクレジットカード連携」の両方で
取り込んでいるケース。この場合、**片方を仕訳しないと二重計上になる。**

```
次の2つが両方つながっています。
  ・◯◯（EC連携）
  ・△△カード

同じ買い物が2回取り込まれるため、どちらか片方だけを仕訳する必要があります。
どちらで仕訳しますか？

  1. EC連携側（商品名が分かるのでおすすめ）
  2. カード側
```

選ばれなかった方を `excluded_patterns` に登録し、**理由も一緒に保存する**
（後から「なぜ仕訳されていないのか」が分かるようにするため）。

**★この設定を他の事業者から流用してはいけない。** 連携していない事業者で同じ除外をすると、
経費が丸ごと計上漏れになる。

## Step 7: 売掛金の扱いを確認する

**自動チェックと本人への確認の両方で決める。**
自動チェックだけに頼ると「たまたま今は未回収がゼロ」の利用者を誤判定し、
後から入金予定が作られたときに二重計上する。

1. `mfc_ca_getJournals(is_realized: false)` を実行する（現時点の未実現仕訳の有無）
2. 利用者に確認する：

```
請求書の発行に「マネーフォワード クラウド請求書」を使っていますか？

  1. 使っている（入金予定を作る設定 / 設定はよく分からない）
  2. 使っているが、「入金予定を作らない」設定にしている
  3. 請求書サービスは使っていない
```

| 判定 | mode |
|---|---|
| 未実現仕訳が1件以上ある／回答1 | `"screen"`（安全側） |
| 回答2または3、かつ未実現仕訳0件 | `"api"` |
| **矛盾**（回答2・3なのに未実現仕訳がある） | 実物を見せて確認。解消するまで `"screen"` |

**`screen` の利用者への説明：**

```
売上を「入金予定」として先に登録する使い方をされていますね。
入金の消し込みはMFの画面で行う必要があるため、そこだけは
私が自動でやらず、対応表をお渡しする形にします。
（自動でやると同じ入金が2回計上されてしまうためです）
```

**`api` の利用者への説明：**

```
入金予定（未実現仕訳）を使わない運用なので、売掛金の回収も
私が仕訳できます。念のため毎回、入金予定が無いことを確認してから
登録します（後で設定を変えても二重計上にならないように）。
```

**★modeが `api` でも、記帳のたびの未実現チェック（mf-import 手順⑤）は絶対に省略しない。**
後から入金予定の運用を始めた利用者を守る最後の砦になる。

## Step 8: 保存して完了

`.mf-cloud/config.json` に保存する。保存先は**証憑を置くフォルダの直下**。
`references/config.example.json` の形式に従う。

最後に、次に何をすればよいかを伝える。**初回は少量で試すことを必ず勧める。**

```
設定が完了しました。

★ 最初は領収書1〜2件で試すことをおすすめします。
   結果をMFクラウドの画面で確認し、科目や税区分が意図どおりか
   確かめてから、まとめて処理してください。
   （設定に誤りがあった場合の影響を最小にするためです）

  今の状況を見る    → /mf-cloud-import:mf-status
  記帳を実行する    → /mf-cloud-import:mf-import
```

---

## やってはいけないこと

- **設定を勝手に決めない。** 全項目、利用者の選択を経る
- **過去仕訳のルールを無断で適用しない。** 必ず件数の根拠を見せて承認を得る
- **税務判断に踏み込まない。** 金額基準や課税方式で迷ったら
  「顧問税理士にご確認ください」と伝え、保留できるようにする
- **他の事業者の設定を流用しない。** 特に除外ルールは事故に直結する
